# Contrato del Workshop 1 — Ride-Sharing Dispatch & Surge Pricing

Este archivo es todo lo que hace falta para entregar una task del Workshop 1
y que aparezca en el dashboard. Se puede pegar completo en una IA: no hace
falta mostrarle el resto del repo.

## Como se entrega una task

1. **Un solo archivo de Python:** `src/w1/taskK_tema.py`, donde K es el numero
   de la task y `tema` una palabra en minusculas (p. ej. `src/w1/task3_hashing.py`).
   No hay que registrarlo en ninguna lista: el dashboard, `run_all.py` y la app
   web lo encuentran por el nombre.
2. **Solo biblioteca estandar** (`csv`, `json`, `math`, `random`, ...). Nada de
   `pip install`: el mismo archivo corre tambien dentro del navegador.
3. **Empieza con este bloque**, tal cual, antes de los demas imports. Es lo que
   hace que el script encuentre los datos desde cualquier carpeta, tambien en
   el navegador:

   ```python
   import os

   BASE = os.path.dirname(os.path.dirname(os.path.dirname(os.path.abspath(__file__))))
   DATA_DIR = os.path.join(BASE, "data")
   RESULTS_DIR = os.path.join(BASE, "results", "w1")
   os.makedirs(DATA_DIR, exist_ok=True)
   os.makedirs(RESULTS_DIR, exist_ok=True)
   RIDES_CSV = os.path.join(DATA_DIR, "rides.csv")
   ```

4. **Todo lo que hace va dentro de `if __name__ == "__main__":`**; arriba del
   archivo solo constantes y funciones.
5. **Reproducible:** si usa azar, semilla fija (`random.seed(...)` o
   `random.Random(...)`). No usar `hash()` de Python para nada que se reporte:
   cambia en cada corrida.
6. **Escribe `results/w1/taskK.json`** con al menos las claves del ejemplo de
   su seccion (abajo). Puede tener mas; el dashboard ignora las que no estan en
   el ejemplo:

   ```python
   with open(os.path.join(RESULTS_DIR, "task3.json"), "w", encoding="utf-8") as f:
       json.dump(resultado, f, indent=2, ensure_ascii=False)
   ```

7. **Revisar antes de subir:**

   ```bash
   python src/w1/dataset.py               # una vez, genera data/rides.csv
   python src/w1/task3_hashing.py         # la task
   python dashboard/contrato.py w1 3      # dice OK o que clave falta
   ```

   Si dice OK, el JSON tiene el formato que lee el panel (claves y tipos; no
   revisa que los numeros esten bien). Para verlo: `cd web && npm install && npm run dev`.

### Como leer los ejemplos

- `"clave": 1.5` es un numero (entero o decimal da igual); `"clave": "texto"`,
  un texto; `true`, un booleano; `null`, cualquier cosa.
- `"clave?"` (con signo de interrogacion) es **opcional**: si la task la
  escribe, se revisa y el panel la usa; si no, no pasa nada. En el JSON va sin
  el signo: `"naive"`, no `"naive?"`.
- En una lista, **cada** elemento debe tener la forma del primero del ejemplo.
- `{"*": 3}` es un diccionario con claves libres (p. ej. una por zona).
- Ningun numero puede ser `NaN` ni infinito: el navegador no los lee.

### La pagina de la task (opcional)

Cada task puede tener una pagina con su explicacion, que tambien sirve de
diapositiva. Es un archivo aparte, `web/lib/docs/w1/taskK.ts`, que solo
importa tipos; no hay que tocar ningun otro archivo de la app:

```ts
import type { TaskDoc } from "@/lib/tasks";
import type { W1Task3 } from "@/lib/generated/contratos";
import { fmt, int } from "@/lib/format";

const doc: TaskDoc<W1Task3> = {
  title: "Titular corto y afirmativo",
  topic: "HASHING UNIVERSAL",
  statement: "El enunciado, en espanol.",
  standfirst: "Resumen sin cifras (se muestra antes de que haya datos).",
  // r es el JSON de la task, con las claves de su ejemplo.
  lede: (r) => `Resumen con cifras: con K=${int(r.universal[0].K)} ...`,
  metrics: (r) => [{ label: "Que es", value: fmt(r.universal[0].avg_desbalance, 2), hint: "de donde sale" }],
  sections: [{ h: "Paso 1", p: "Explicacion." }],
  takeaway: "La frase de cierre.",
};
export default doc;
```

`W1Task3` (y `W1Task1`, `W1Task2`, ...) se generan solos a partir de los
ejemplos de este archivo: el editor autocompleta las claves.

## Los datos

`src/w1/dataset.py` escribe `data/rides.csv` (~495.000 filas, 14 dias, 10
zonas). Columnas:

| columna | tipo | ejemplo |
|---|---|---|
| ride_id | texto | `b3cfd7280b5c` |
| timestamp | texto ISO | `2026-09-01T00:00:03` |
| rider_id | texto | `rdr_14534` |
| driver_id | texto | `drv_00150` |
| pickup_zone | texto | `AIRPORT` |
| distance_km | decimal | `3.87` |
| fare | decimal | `9649.0` |

La demanda de cada zona es un proceso de Poisson con una tasa distinta por
hora del dia, asi que hay picos por zona y por hora.

## Task 1 — Contexto de Big Data

Estimar las solicitudes por segundo de toda la ciudad en la hora pico, y el
almacenamiento con un crecimiento de 10x.

- `total_requests`: filas de rides.csv.
- `n_days`: dias simulados.
- `peak_req_per_sec`: solicitudes por segundo en la hora con mas solicitudes de toda la ciudad.
- `peak_req_per_sec_10x`: lo mismo si la demanda crece 10x.
- `storage_year_gb`: GB por ano del log de solicitudes con la demanda actual.
- `storage_year_10x_gb`: GB por ano con 10x.

```json
{
  "total_requests": 495505,
  "n_days": 14,
  "peak_req_per_sec": 0.86,
  "peak_req_per_sec_10x": 8.61,
  "storage_year_gb": 2.19,
  "storage_year_10x_gb": 21.9
}
```

## Task 2 — Algoritmo aleatorizado

QuickSort aleatorizado para rankear viajes por tarifa, contra un QuickSort
determinista, en varios tamanos de entrada.

- `quicksort`: una fila por (tamano, tipo de entrada, algoritmo).
  - `n`: cuantas tarifas se ordenan.
  - `input`: `"random_input"` (orden original) o `"sorted_input"` (ya ordenada: el peor caso del pivote fijo).
  - `algorithm`: `"randomized_quicksort"` o `"deterministic_quicksort"`.
  - `time_s`: segundos que tardo una corrida de ese algoritmo sobre esa entrada.
  - `comparisons`, `expected_comparisons`: comparaciones contadas y las 2n ln n de la teoria.
  - `recursion_overflow`: en las filas del determinista, si desbordo la recursion (su tiempo no cuenta).
- `fare_distribution`: cuantas tarifas distintas hay (el 2n ln n supone que todas lo son).

```json
{
  "quicksort": [
    {
      "n": 500,
      "input": "random_input",
      "algorithm": "randomized_quicksort",
      "time_s": 0.0013,
      "comparisons?": 4598,
      "expected_comparisons?": 6215.0,
      "recursion_overflow?": false
    }
  ],
  "fare_distribution?": {
    "n_total": 495505,
    "n_distinct": 25474,
    "avg_repeats": 19.45,
    "max_repeats": 4533
  }
}
```

## Task 3 — Hashing universal

Hashear `driver_id` para repartir las solicitudes entre K procesos de
despacho y medir las colisiones, para varios K.

- `universal`: una fila por K, con la familia universal h(x) = ((a x + b) mod p) mod K.
  - `K`: numero de procesos (buckets).
  - `avg_desbalance`: carga del bucket mas cargado / carga media, promediada sobre las repeticiones. El ideal es 1.
  - `avg_collisions_empirical`: pares de conductores que caen en el mismo bucket.
  - `theoretical_expected_collisions`: la cota C(n, 2) / K de clase, con n = conductores distintos.
- `naive` (opcional): lo mismo con un hash ingenuo, para comparar.

```json
{
  "universal": [
    {
      "K": 16,
      "avg_desbalance": 1.21,
      "avg_collisions_empirical": 44914.1,
      "theoretical_expected_collisions": 44962.5
    }
  ],
  "naive?": [
    {
      "K": 16,
      "desbalance": 1.2,
      "collisions_empirical": 45459
    }
  ]
}
```

## Task 4 — Tabla hash

Tabla hash indexada por `pickup_zone` para agrupar las solicitudes
concurrentes (misma zona, misma ventana de minutos), comparando
encadenamiento contra power-of-two-choices.

Hay dos capas de hashing. La exterior es el indice por zona: un diccionario
con clave (`pickup_zone`, ventana de 5 minutos) que junta las solicitudes que
compiten a la vez en el mismo sitio. La interior reparte las solicitudes de
cada grupo entre B colas hasheando su `ride_id`, una vez (encadenamiento) o
dos (power-of-two-choices). Hashear `pickup_zone` en la capa interior no
serviria: todas las solicitudes del grupo tienen la misma zona e irian a la
misma cola.

- `summary`: el promedio sobre todas las ventanas.
  - `B_buckets`: colas de despacho.
  - `n_windows_analyzed`: ventanas (zona, 5 minutos) analizadas; se excluyen las de menos de 2 solicitudes.
  - `avg_max_load_chaining`, `avg_max_load_p2c`: carga maxima promedio con cada metodo.
  - `worst_max_load_chaining`, `worst_max_load_p2c`: la peor carga maxima vista.
- `top_windows`: las ventanas con mas solicitudes, de mayor a menor. El panel dibuja la primera.
  - `loads`: solicitudes en cada uno de los `B_buckets` buckets.
  - `theory` (opcional): carga media y una aproximacion de la carga maxima en ese regimen (referencia de orden de magnitud, sin el termino O(1); no es una cota que cada ventana deba respetar).

```json
{
  "summary": {
    "B_buckets": 16,
    "n_windows_analyzed": 34613,
    "avg_max_load_chaining": 2.688,
    "avg_max_load_p2c": 1.918,
    "worst_max_load_chaining": 13,
    "worst_max_load_p2c": 8,
    "theory_note?": "texto que explica la referencia teorica"
  },
  "top_windows": [
    {
      "zone": "EL_POBLADO",
      "minute": "2026-09-06T18:30",
      "n_requests": 101,
      "chaining": { "loads": [5, 5, 7, 7, 5, 6, 10, 4, 4, 8, 4, 6, 2, 8, 12, 8], "max_load": 12 },
      "power_of_two_choices": { "loads": [6, 7, 6, 7, 6, 6, 6, 6, 6, 7, 5, 8, 6, 6, 7, 6], "max_load": 8 },
      "theory?": { "avg_load": 6.312, "chaining_expected_max": 12.23, "p2c_expected_max": 7.78 }
```

## Task 5 — Analisis de probabilidad

Chernoff o Chebyshev para acotar la probabilidad de que una zona reciba un
numero inusualmente alto de solicitudes (la senal para activar surge).

- `k_sigma`: el surge se activa cuando el conteo supera mu + k sigma.
- `zones`: una fila por zona, en su hora de mayor demanda.
  - `peak_hour`: hora del dia (0-23).
  - `mu`: media de solicitudes en esa hora, sobre los dias simulados.
  - `sigma_model_sqrt_mu`: sigma del modelo Poisson, raiz de mu.
  - `sigma_hat`: desviacion observada en los dias simulados.
  - `daily_counts_observed` (opcional): el conteo de cada dia; el panel los superpone a la curva teorica.
  - `model_based.surge_threshold`: el umbral mu + k sigma.
  - `model_based.chebyshev_bound`, `model_based.chernoff_bound`: las dos cotas de P(X >= umbral). Como el evento es de una sola cola, `chebyshev_bound` es la version unilateral (Cantelli), 1 / (1 + k^2), no el 1 / k^2 de la Chebyshev bilateral; la clave conserva el nombre.
  - `model_based.monte_carlo_prob`: esa probabilidad estimada por simulacion.

```json
{
  "k_sigma": 2.0,
  "zones": [
    {
      "zone": "AIRPORT",
      "peak_hour": 18,
      "mu": 324.43,
      "sigma_model_sqrt_mu": 18.012,
      "sigma_hat": 18.409,
      "daily_counts_observed?": [305, 331, 318],
      "model_based": {
        "surge_threshold": 361,
        "chebyshev_bound": 0.2,
        "chernoff_bound": 0.145173,
        "monte_carlo_prob": 0.02386
      }
    }
  ]
}
```
