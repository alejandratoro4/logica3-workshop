# Contrato del Workshop 4 — El grafo de reubicaciones como jobs de MapReduce

Este archivo es todo lo que hace falta para entregar una task del Workshop 4
y que aparezca en el dashboard. Se puede pegar completo en una IA: no hace
falta mostrarle el resto del repo, salvo `src/w4/mapreduce.py` (el runner),
que conviene pegar tambien.

## Como se entrega una task

1. **Un solo archivo de Python:** `src/w4/taskK_tema.py`, donde K es el numero
   de la task y `tema` una palabra en minusculas (p. ej. `src/w4/task3_costo.py`).
   No hay que registrarlo en ninguna lista: el dashboard, `run_all.py` y la app
   web lo encuentran por el nombre.
2. **Solo biblioteca estandar** (`csv`, `json`, `math`, `time`, ...). Nada de
   `pip install` (ni numpy, ni pyspark): el mismo archivo corre tambien en el
   navegador.
3. **Empieza con este bloque**, tal cual, antes de los demas imports. Las dos
   ultimas lineas traen el runner de MapReduce del workshop:

   ```python
   import os

   BASE = os.path.dirname(os.path.dirname(os.path.dirname(os.path.abspath(__file__))))
   DATA_DIR = os.path.join(BASE, "data")
   RESULTS_DIR = os.path.join(BASE, "results", "w4")
   os.makedirs(DATA_DIR, exist_ok=True)
   os.makedirs(RESULTS_DIR, exist_ok=True)
   EDGES_CSV = os.path.join(DATA_DIR, "edges.csv")
   NODES_CSV = os.path.join(DATA_DIR, "nodes.csv")

   import sys
   sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))
   from mapreduce import Cluster, fragmentos, dividir
   ```

4. **Todo lo que hace va dentro de `if __name__ == "__main__":`**; arriba del
   archivo solo constantes y funciones. Aqui no es solo orden: cada proceso
   del pool vuelve a importar el script, y lo que este arriba se ejecutaria
   una vez por proceso.
5. **Los map, reduce y combiner son funciones de nivel superior** (definidas
   con `def` arriba del archivo). Nada de `lambda` ni de funciones definidas
   dentro de otras: los procesos las buscan por nombre. Si un map necesita
   un dato extra (el vector v de PageRank), va dentro de cada registro de
   entrada o con `functools.partial(mi_map, v)`.
6. **Los jobs corren con el runner**, no con un bucle propio: asi el shuffle,
   la carga por reducer y los tiempos se miden igual en todas las tasks.
7. **Las tasks no leen el JSON de otra task:** cada una se puede entregar y
   revisar sola. Si una necesita algo de otra (la Task 3 necesita las
   iteraciones de PageRank de la Task 2), lo vuelve a calcular.
8. **Reproducible:** si usa azar, semilla fija (`random.Random(42)`). Los
   tiempos cambian en cada corrida; todo lo demas no.
9. **Escribe `results/w4/taskK.json`** con al menos las claves del ejemplo de
   su seccion (abajo). Puede tener mas; el dashboard ignora las que no estan:

   ```python
   with open(os.path.join(RESULTS_DIR, "task3.json"), "w", encoding="utf-8") as f:
       json.dump(resultado, f, indent=2, ensure_ascii=False)
   ```

10. **Revisar antes de subir:**

    ```bash
    python run_all.py w4                   # genera los datasets w1..w4 y corre lo que haya
    python src/w4/task3_costo.py           # o solo la task
    python dashboard/contrato.py w4 3      # dice OK o que clave falta
    ```

    Si dice OK, el JSON tiene el formato que lee el panel (claves y tipos; no
    revisa que los numeros esten bien). Para verlo: `cd web && npm install && npm run dev`.

### Como leer los ejemplos

- `"clave": 1.5` es un numero (entero o decimal da igual); `"clave": "texto"`,
  un texto; `true`, un booleano; `null`, cualquier cosa.
- `"clave?"` (con signo de interrogacion) es **opcional**: si la task la
  escribe, se revisa y el panel la usa; si no, no pasa nada. En el JSON va sin
  el signo.
- En una lista, **cada** elemento debe tener la forma del primero del ejemplo.
- `{"*": 3}` es un diccionario con claves libres (p. ej. una por zona).
- Ningun numero puede ser `NaN` ni infinito: el navegador no los lee.

### El runner (`src/w4/mapreduce.py`)

```python
def map_viajes(fila):                      # un registro -> pares (clave, valor)
    yield fila["driver_id"], (int(fila["stream_seq"]), fila["pickup_zone"])

def reduce_conductor(driver, viajes):      # una clave y TODOS sus valores
    viajes.sort()
    for (_, a), (_, b) in zip(viajes, viajes[1:]):
        yield (a, b), 1

if __name__ == "__main__":
    with Cluster(workers=4) as c:                         # un pool de 4 procesos
        r = c.ejecutar("1a", fragmentos(), map_viajes, reduce_conductor, reducers=4)
        r.salida        # [(clave, valor), ...] ordenada por clave
        r.por_reducer   # la salida de cada reduce task: los splits de la ronda siguiente
        r.stats         # las cifras de abajo
```

- `fragmentos(copias=1)`: los splits de `data/w4/`, uno por archivo.
  `fragmentos(2)` y `fragmentos(4)` son el dataset 2x y 4x: cada copia
  repite los archivos con los `driver_id` renombrados (`drv_00042#1`), asi
  que son conductores nuevos con los mismos viajes y el grafo sale
  exactamente al doble o al cuadruple.
- `dividir(lista, n)`: parte una lista en memoria en n splits (las aristas
  del Job 2, las entradas de la matriz en PageRank).
- `c.ejecutar(job, splits, mapper, reducer, combiner=None, reducers=4)`: una
  map task por split y `reducers` reduce tasks. El combiner tiene la forma
  del reducer y corre en cada map task sobre su propia salida.
- Con `workers > 1` los map y los reduce corren en procesos de verdad. El
  arranque del pool no entra en los tiempos (queda en `c.arranque_s`). Cada
  map task serializa sus particiones y cada reduce task abre las suyas; el
  proceso principal solo reenvia los bytes, asi que el costo del shuffle
  queda dentro de `map_s` y `reduce_s` (serializar, mandar entre procesos,
  deserializar) y `shuffle_s` sale casi en cero.
- **En el navegador no hay procesos:** todo corre en secuencia y
  `stats["parallel"]` es `False`. Los resultados son los mismos; los tiempos
  no sirven para medir speedup. Los numeros que se exponen salen de la
  terminal.

Lo que mide el runner (`r.stats`), con estas claves:

| clave | que es |
|---|---|
| `job` | el nombre que se le dio |
| `map_tasks`, `reduce_tasks`, `workers`, `parallel` | como corrio |
| `input_records` | registros leidos por las map tasks |
| `map_output_pairs` | pares que emitio el map, antes del combiner |
| `shuffle_pairs` | pares que viajaron a los reducers, despues del combiner |
| `shuffle_bytes` | bytes de esos pares serializados (pickle): el tamano del shuffle |
| `reducer_loads` | pares que recibio cada reduce task |
| `max_reducer_load` | el maximo de la lista anterior |
| `distinct_keys` | claves distintas |
| `max_key_values` | valores de la clave mas cargada: el tamano de reducer **q** |
| `hot_key` | esa clave, como texto (un par de zonas sale `"AIRPORT -> BELEN"`); si varias empatan, la menor |
| `hot_key_ties` | cuantas claves tienen ese maximo (1 = no hay empate) |
| `output_records` | pares que emitieron los reducers |
| `map_s`, `shuffle_s`, `reduce_s`, `total_s` | segundos de cada fase y del job |

Notacion del curso (Mining of Massive Datasets, cap. 2): el **costo de
comunicacion** de un algoritmo es la suma del tamano de la entrada de todas
sus tareas; la **tasa de replicacion** r es el numero de pares que emite el
map por cada registro de entrada (`map_output_pairs / input_records`), y el
**tamano de reducer** q es el maximo de valores que recibe una sola clave.

Ojo con el combiner: cambia lo que llega a los reducers, no lo que emite el
map. Sin combiner, `map_output_pairs` = `shuffle_pairs` y las dos formas de r
del curso (pares del map por entrada; entradas de los reduce por entradas de
los map) coinciden. Con combiner, `max_key_values` cuenta valores ya
combinados: en 1b sale el numero de map tasks, no el `reloc_count` del par
mas frecuente.

Una fase no usa mas workers que tareas: el map tiene una tarea por split y
el reduce, `reducers` (4 si no se dice). Los splits de 1b son la salida de 1a
(`r1a.por_reducer`), asi que 1b tiene tantas map tasks como reducers tuvo 1a.

## Task 1 — Pipeline MapReduce

Job 1: el map emite `(driver_id, (stream_seq, pickup_zone))`; el reduce
ordena los viajes de cada conductor por `stream_seq` y emite un par
`((zona_i, zona_siguiente), 1)` por reubicacion, y esos pares se suman en
`reloc_count`. Job 2: el map emite `(zona, (salen, llegan))` desde las
aristas; el reduce arma el resumen por zona. Correr el map en paralelo sobre
los 8 fragmentos con 2 o mas workers y validar las aristas contra la
Unidad 3.

El Job 1 son dos rondas, porque contar los pares necesita otro shuffle
(ahora por par de zonas):

- **`"1a"`**: agrupar por conductor. Entrada: `fragmentos()`. Para validar
  tambien `avg_fare` y `avg_wait_for_driver_sec`, el valor de cada viaje
  puede llevar la tarifa y la espera, y el reduce emitir
  `((a, b), (1, tarifa, espera))` con las del viaje en `b`.
- **`"1b"`**: sumar por par de zonas, con el mismo reduce como combiner.
  Entrada: `r1a.por_reducer`. Para que el reduce sirva de combiner, su
  salida tiene que tener la forma de lo que recibe: sumas
  `(n, suma_tarifa, suma_espera)`, no medias (la media de medias da otro
  numero sin ningun error). Las medias se sacan al final.
- **`"2"`**: el resumen por zona desde las aristas de 1b
  (`dividir(r1b.salida, n)`). Cada arista (a, b) con sus sumas emite
  `(a, (n, 0, 0, 0))` por la salida y `(b, (0, n, suma_tarifa, suma_espera))`
  por la llegada; el reduce suma y divide. Asi salen los conteos y las
  medias de `nodes.csv` (las medias son de los viajes que llegan).

- `n_fragments`, `workers`, `parallel`: como corrio.
- `jobs`: los `stats` de los tres jobs, en orden (`"1a"`, `"1b"`, `"2"`), tal cual los da el runner.
- `validation`: las aristas del Job 1 contra `data/edges.csv`.
  - `edges_match`: mismos pares, mismo `reloc_count` y medias a 0.01 o menos.
  - `max_diff_*`: la mayor diferencia absoluta en cada columna.
- `nodes`: la salida del Job 2, una fila por zona, con las columnas de `nodes.csv`.
- `nodes_match` (opcional): si coincide con `data/nodes.csv`.

## Task 2 — PageRank como producto matriz-vector

S10: una ronda de MapReduce = una multiplicacion de PageRank sobre el grafo de
reubicaciones. El map emite `(j, p(i,j) * v_i)` y el reduce suma por j. Iterar
hasta que ||v(t+1) - v(t)||_1 < 1e-6 y comparar con la Unidad 3 (deben
coincidir a 1e-4).

- M por filas, como en el W3: `p(i,j)` = reloc_count(i -> j) / total que sale
  de i, desde `data/edges.csv`. Cada registro de entrada de una ronda es una
  entrada de la matriz con el valor de v que le toca, `(i, j, p_ij, v_i)`
  (asi el map no necesita leer v de otro lado).
- PageRank con teletransporte, `beta = 0.85`, desde v uniforme:
  `v'_j = beta * suma_i p(i,j) v_i + (1 - beta) / n`. El reduce puede aplicar
  el teletransporte al sumar.
- "La Unidad 3": el mismo PageRank calculado en memoria, como la Task 3 del
  W3 (sin MapReduce, iterando hasta 1e-10). La task lo calcula ella misma.

- `beta`, `tol`, `iterations`, `converged`.
- `rounds`: una fila por iteracion.
  - `l1_change`: ||v(t+1) - v(t)||_1 de esa iteracion.
  - `map_output_pairs`, `shuffle_pairs`, `time_s`: de los `stats` de esa ronda.
- `zones`: una fila por zona, con `pagerank_mr` (MapReduce), `pagerank_unit3` y `abs_diff`.
- `max_abs_diff`, `agrees_1e4`: la mayor diferencia y si es menor que 1e-4.

```json

  "tol": 1e-6,
  "iterations": 5,
  "converged": true,
  "rounds": [
```

## Task 5 — Eficiencia paralela

S13, escalamiento con claves balanceadas: medir el pipeline completo (los
jobs 1a, 1b y 2 de la Task 1) con P = 1, 2, 4, 8 workers en 2 o mas tamanos de
datos; reportar el speedup S_P = T_1 / T_P y la eficiencia E_P = S_P / P y
explicar donde cae la eficiencia.

- Un `Cluster(workers=P)` por P; el tiempo es la suma de `total_s` de los tres
  jobs, sin el arranque del pool. Si repites cada medicion, reporta la mediana.
- **El mismo `reducers` para todos los P, y al menos el P mas alto**
  (`reducers=8`): asi el job es identico y solo cambian los workers. Con el
  valor por defecto (4), a P = 8 la mitad del pool espera en cada reduce y
  en el map de 1b; medido a 1x en una maquina de 16 nucleos, P = 8 tarda
  2,07 s con R = 4 y 1,65 s con R = 16.
- `parallel`: la constante `PARALELO` del runner
  (`from mapreduce import PARALELO`): `true` en la terminal, `false` en el
  navegador, y ahi el panel avisa. **No** el `stats["parallel"]` del run con
  P = 1, que es `false` tambien en la terminal porque ese job corrio en un
  solo proceso.
- `cpu_count`: `os.cpu_count()` de la maquina donde corrio.
- `runs`: una fila por (escala, P).
  - `speedup`, `efficiency`: contra el P = 1 de la misma escala.
  - `map_s`, `shuffle_s`, `reduce_s` (opcionales): el tiempo por fase, sumado sobre los tres jobs. Sirven para ver que fase no escala.

```json
{
```

ultimo viaje de cada conductor fueran independientes y salieran de la misma
distribucion por zona (estimada juntando ambos): raiz de 2 D p (1 - p), con
p = (first + last) / 2D.
`first_ride_median_h` y `last_ride_median_h` dicen cuando empiezan y terminan
los conductores (mediana, en horas desde la medianoche del primer dia):
`net_flow` compara la demanda de cada zona a esas dos horas.
