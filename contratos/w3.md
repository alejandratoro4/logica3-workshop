# Contrato del Workshop 3 — Cadenas de Markov sobre las reubicaciones de conductores

Este archivo es todo lo que hace falta para entregar una task del Workshop 3
y que aparezca en el dashboard. Se puede pegar completo en una IA: no hace
falta mostrarle el resto del repo.

## Como se entrega una task

1. **Un solo archivo de Python:** `src/w3/taskK_tema.py`, donde K es el numero
   de la task y `tema` una palabra en minusculas (p. ej. `src/w3/task3_pagerank.py`).
   No hay que registrarlo en ninguna lista: el dashboard, `run_all.py` y la app
   web lo encuentran por el nombre.
2. **Solo biblioteca estandar** (`csv`, `json`, `math`, `random`, ...). Nada de
   `pip install` (ni numpy): el mismo archivo corre tambien en el navegador.
   Con 10 zonas, las matrices son listas de listas de 10 x 10.
3. **Empieza con este bloque**, tal cual, antes de los demas imports:

   ```python
   import os

   BASE = os.path.dirname(os.path.dirname(os.path.dirname(os.path.abspath(__file__))))
   DATA_DIR = os.path.join(BASE, "data")
   RESULTS_DIR = os.path.join(BASE, "results", "w3")
   os.makedirs(DATA_DIR, exist_ok=True)
   os.makedirs(RESULTS_DIR, exist_ok=True)
   EDGES_CSV = os.path.join(DATA_DIR, "edges.csv")
   RIDES_CSV = os.path.join(DATA_DIR, "rides.csv")
   ```

4. **Todo lo que hace va dentro de `if __name__ == "__main__":`**; arriba del
   archivo solo constantes y funciones.
5. **Cada task lee `edges.csv` y arma su propia matriz.** Las tasks no leen el
   JSON de otra task: asi cada una se puede entregar y revisar sola.
6. **Reproducible:** si usa azar, semilla fija (`random.Random(42)`).
7. **Escribe `results/w3/taskK.json`** con al menos las claves del ejemplo de
   su seccion (abajo). Puede tener mas; el dashboard ignora las que no estan:

   ```python
   with open(os.path.join(RESULTS_DIR, "task3.json"), "w", encoding="utf-8") as f:
       json.dump(resultado, f, indent=2, ensure_ascii=False)
   ```

8. **Revisar antes de subir:**

   ```bash
   python run_all.py w3                   # genera rides.csv, stream.csv y edges.csv, y corre lo que haya
   python src/w3/task3_pagerank.py        # o solo la task
   python dashboard/contrato.py w3 3      # dice OK o que clave falta
   ```

   Si dice OK, el JSON tiene el formato que lee el panel (claves y tipos; no
   revisa que los numeros esten bien). Para verlo: `cd web && npm install && npm run dev`.

### Como leer los ejemplos

- `"clave": 1.5` es un numero (entero o decimal da igual); `"clave": "texto"`,
  un texto; `true`, un booleano; `null`, cualquier cosa.
- `"clave?"` (con signo de interrogacion) es **opcional**: si la task la
  escribe, se revisa y el panel la usa; si no, no pasa nada. En el JSON va sin
  el signo.
- En una lista, **cada** elemento debe tener la forma del primero del ejemplo.
- `{"*": 3}` es un diccionario con claves libres (p. ej. una por zona).
- Ningun numero puede ser `NaN` ni infinito: el navegador no los lee.

### La pagina de la task (opcional)

Cada task puede tener una pagina con su explicacion, que tambien sirve de
diapositiva. Es un archivo aparte, `web/lib/docs/w3/taskK.ts`; no hay que
tocar ningun otro archivo de la app:

import type { TaskDoc } from "@/lib/tasks";

  // r es el JSON de la task, con las claves de su ejemplo.

`W3Task3` (y los demas) se generan solos a partir de los ejemplos de este
archivo: el editor autocompleta las claves.

## Los datos

`src/w3/dataset.py` lee `data/stream.csv` (el del Workshop 2) y escribe
`data/edges.csv`, el grafo de reubicaciones del enunciado: para cada
conductor, en orden de `stream_seq`, una arista desde la zona de un viaje
hasta la zona del siguiente viaje de ese conductor. Si el siguiente viaje es en
la misma zona, la arista es un lazo (`from_zone == to_zone`). Una fila por par
de zonas observado; con 10 zonas, hasta 100 filas.

Que esperar de este grafo: en el W1 el conductor de cada viaje se sortea al
azar, asi que la zona del siguiente viaje no depende de la del anterior. Las
filas de M salen casi iguales (difieren en menos de 0.02), pi queda muy cerca
de la participacion de cada zona en los viajes y PageRank ordena las zonas
igual que el volumen en la corrida canonica. Es un resultado valido: hay que
reportarlo y explicarlo asi, no forzar diferencias. Con otros parametros (pocos
dias, escala chica) dos zonas de volumen parecido pueden cambiar de puesto por
ruido de muestreo.

El mismo script escribe tambien `data/edges_despacho.csv`, un escenario
alterno con despacho espacial (cada viaje lo toma el conductor libre mas
cercano). Lo usa solo el dashboard (Task 6); **las Tasks 1 a 5 leen
`edges.csv`**.

| columna | tipo | ejemplo |
|---|---|---|
| edge_id | texto | `e001` |
| from_zone | texto | `AIRPORT` |
| to_zone | texto | `BELEN` |
| reloc_count | entero | `5473` |
| avg_fare | decimal | `10133.8` (tarifa media del viaje en `to_zone`) |
| avg_wait_for_driver_sec | decimal | `67.65` (espera media de ese viaje) |

El conteo de viajes por zona de la Unidad 1 sale de `data/rides.csv` (columna
`pickup_zone`), que tambien esta disponible.

Notacion del curso: M es la matriz de transicion con **M[i][j] = P(ir de la
zona i a la zona j)**, cada fila suma 1, y la distribucion estacionaria
cumple **pi = pi M**.

## Task 1 — Construccion de la DTMC y clasificacion de estados

Estados = zonas de recogida (8 o mas). Construir M a partir de
`reloc_count`. Hay alguna zona absorbente ("zona muerta": los conductores
llegan pero nunca salen)?

- `states`: las zonas, en el orden de las filas y columnas de M.
- `matrix`: M, con `matrix[i][j]` = reloc_count(i -> j) / total que sale de i.
- `absorbing`: zonas con M[i][i] = 1 (lista vacia si no hay).
- `irreducible`: si desde cualquier zona se llega a cualquier otra.
- `aperiodic`: si la cadena es aperiodica.
- `classes` (opcional): las clases de comunicacion y si son recurrentes o transitorias.

```json
{
  "states": ["AIRPORT", "BELEN"],
  "matrix": [[0.13, 0.87], [0.4, 0.6]],
  "absorbing": [],
  "irreducible": true,
  "aperiodic": true,
  "classes?": [
    { "states": ["AIRPORT", "BELEN"], "type": "recurrente" }
  ]
}
```

## Task 2 — Distribucion estacionaria

Interpretar pi: en que zonas pasan mas tiempo los conductores a largo plazo.
Compararla con el conteo de viajes por zona de la Unidad 1.

Ojo con "tiempo": la cadena salta de una recogida a la siguiente, asi que pi_i
es la fraccion de las **recogidas** (pasos de la cadena) que caen en la zona i
a largo plazo, no de las horas de reloj. Tampoco es exactamente la
participacion en viajes: el primer y el ultimo viaje de cada conductor solo
aportan una arista, y eso deja diferencias pequenas.

- `method`: como se calculo pi (p. ej. `"potencias"`, `"sistema lineal"`).
- `zones`: una fila por zona.
  - `pi`: probabilidad estacionaria (suman 1).
  - `ride_count`: viajes de esa zona en `rides.csv` (Unidad 1).
- `iterations` (opcional): iteraciones del metodo de potencias.

```json
{
  "method": "potencias",
  "iterations?": 12,
  "zones": [
    { "zone": "AIRPORT", "pi": 0.1411, "ride_count": 69900 }
  ]
}
```

## Task 3 — PageRank

PageRank estandar: rankear las zonas y comparar contra el ranking por volumen
de viajes; explicar una zona que quede mas arriba en PageRank que en volumen.

Usa `reloc_count` como peso de cada arista (desde la zona i se sigue la arista
i -> j con probabilidad proporcional a su reloc_count), es decir, la M de la
Task 1. Sin pesos el grafo es completo, porque se observan los 100 pares de
zonas, y todas las zonas empatan en PageRank.

Ojo con la orientacion: el notebook de PageRank itera
v = beta M v + (1 - beta) e / n con M **por columnas** (M[j][i] = P(i -> j)),
que es la traspuesta de la M por filas de la Task 1. Si usas la M de la
Task 1 en esa formula, trasponla primero (o itera v = beta v M + (1 - beta) e / n
con v como fila).

- `beta`: probabilidad de seguir una arista (1 - beta es la de teletransportarse).
- `iterations`: iteraciones hasta converger.
- `zones`: una fila por zona.
  - `pagerank`: su valor (suman 1).
  - `pagerank_rank`, `volume_rank`: puesto en cada ranking (1 = el primero).
  - `ride_volume`: viajes de la zona, el criterio del ranking por volumen.
- `explanation`: la zona que sube en PageRank respecto a su volumen y por que (lo pide el enunciado). Si ninguna sube, dilo y explica por que.

```json
{
  "beta": 0.85,
  "iterations": 30,
  "zones": [
    { "zone": "AIRPORT", "pagerank": 0.1349, "pagerank_rank": 2, "ride_volume": 70004, "volume_rank": 2 }
  ],
  "explanation": "<zona> sube porque ..."
}
```

## Task 4 — Caminata aleatoria

Simetrizar el grafo, hacer una caminata aleatoria de 50.000 pasos o mas y
verificar las visitas empiricas contra pi_i = d_i / (2|E|).

- `steps`: pasos de la caminata.
- `n_edges`: |E| del grafo simetrizado. La forma natural es un **multigrafo**: cada reubicacion es una arista no dirigida entre sus dos zonas. Asi la formula del curso (pi_i = d_i / 2|E|, con |E| aristas) vale tal cual: |E| es el total de reubicaciones, d_i cuenta las aristas que tocan la zona i, y un lazo (i -> i) suma 2 a d_i, como en cualquier grafo no dirigido. La caminata elige el siguiente paso entre las aristas de su zona, con lazos incluidos. Si en cambio se usa el grafo simple (una arista por par de zonas), queda completo y la pi teorica sale uniforme. Explica en la pagina cual usaste.
- `zones`: una fila por zona.
  - `degree`: d_i.
  - `pi_theory`: d_i / (2|E|).
  - `pi_empirical`: visitas / pasos.
- `convergence` (opcional): distancia entre la empirica y la teorica a medida que avanza la caminata.

```json
{
  "steps": 50000,
  "n_edges": 494305,
  "zones": [
    { "zone": "AIRPORT", "degree": 138920, "pi_theory": 0.1405, "pi_empirical": 0.1398 }
  ],
  "convergence?": [
    { "step": 1000, "tv_distance": 0.031 }
  ]
}
```

## Task 5 — 2-SAT aleatorizado

Algoritmo de Papadimitriou: 5 restricciones de politica de despacho sobre 8
o mas variables (p. ej. "si la probabilidad estacionaria de la zona X es alta,
entonces o el surge esta activo en X o se envian conductores extra a X").

Formato de los literales: `"x3"` es la variable x3 verdadera y `"-x3"`, su
negacion. Cada clausula tiene exactamente 2 literales.

Ojo con las condiciones como "si pi(X) es alta". Si "pi(X) es alta" fuera una
variable p, la restriccion quedaria (no p o surge o extra): 3 literales, y eso
ya no es 2-SAT. Lo que se hace es evaluar la condicion con los datos (la pi de
la Task 2): si se cumple, la restriccion entra como la clausula (surge o
extra); si no, no aplica. Tampoco vale partirla en (no p o surge) y (no p o
extra): eso exige surge Y extra, que es otra regla.

- `variables`: cada variable y que significa.
- `constraints`: las 5 restricciones, cada una con su texto y las clausulas en que se traduce.
- `satisfiable`: si encontro una asignacion que cumple todo. `false` solo dice que agoto `max_flips` sin encontrarla, no que la formula sea insatisfacible: el algoritmo es aleatorizado y puede fallar con probabilidad a lo sumo 1/2^b.
- `assignment`: el valor final de cada variable (`{"x1": true, "x2": false, ...}`).
- `flips`: cambios de variable que hizo hasta terminar.
- `max_flips`: el limite de cambios que usaste. El curso corre el algoritmo con t = 2 n^2 cambios: como el numero esperado de cambios es a lo sumo n^2, por la desigualdad de Markov falla con probabilidad a lo sumo 1/2. Repetirlo b veces (2 b n^2 cambios en total) baja el fallo a 1/2^b; el notebook lo escribe como t = 2^b n^2, que tambien cumple porque es mas largo.
- `trace` (opcional): clausulas sin cumplir despues de cada cambio, para dibujar la caminata.

```json
{
  "variables": [
    { "name": "x1", "meaning": "surge activo en DOWNTOWN" }
  ],
  "constraints": [
    {
      "text": "si pi(DOWNTOWN) es alta, surge en DOWNTOWN o conductores extra a DOWNTOWN",
      "clauses": [["x1", "x2"]]
    }
  ],
  "satisfiable": true,
  "assignment": { "*": true },
  "flips": 14,
  "max_flips": 1280,
  "trace?": [3, 2, 2, 1, 0]
}
```
